# Implementation Decisions

## Stage C: Mock authentication and authorization

- **Authentication mode:** Development-only email/password login issues signed bearer access tokens. The authentication service, token helpers, password hashing helpers, route schemas, and FastAPI dependencies are separate modules so a later identity provider can replace the mock login without changing business routes.
- **Token format:** PyJWT signs HS256 tokens containing the database user ID in `sub`, a role claim, `iat`, and `exp`. `JWT_SECRET` is read from backend environment configuration and must be at least 32 characters. `ACCESS_TOKEN_EXPIRE_MINUTES` defaults to 30.
- **Environment and demo restriction:** `APP_ENV` is required and must be one of `development`, `test`, `staging`, or `production`; there is no environment fallback. Public demo accounts may only be seeded or authenticated when `APP_ENV=development`. In other environments, `seed_database()` rejects demo seeding. `seed_database(include_demo_accounts=False)` can still seed SYSTEM and baseline settings without creating public demo accounts.
- **Token lifetime:** `ACCESS_TOKEN_EXPIRE_MINUTES` accepts 1 through 1440 minutes, inclusive. The default remains 30 minutes.
- **Password storage:** `pwdlib` with its recommended Argon2id configuration hashes demo passwords. Plaintext passwords are read from local environment variables only during seeding. Hashes are stored in `users.password_hash`; plaintext values are never stored in the database. The field is nullable so the SYSTEM account can remain passwordless, and a database check prevents SYSTEM from receiving a password hash.
- **Demo accounts:** `member@concave.test`, `agent@concave.test`, and `head@concave.test` represent MEMBER, SUPPORT_AGENT, and SUPPORT_HEAD. Their local sample passwords are `MemberDemoOnly!2026`, `AgentDemoOnly!2026`, and `HeadDemoOnly!2026`. These public demonstration credentials must never be used outside local development. Configure `DEMO_MEMBER_PASSWORD`, `DEMO_AGENT_PASSWORD`, and `DEMO_HEAD_PASSWORD` in `backend/.env` before the first seed. Demo password settings must contain 12–128 characters. The idempotent seed hashes the configured values when an account has no hash; subsequent seed runs preserve existing hashes.
- **SYSTEM exclusion:** `system@concave.internal` has role SYSTEM and no password hash. Login only accepts MEMBER, SUPPORT_AGENT, and SUPPORT_HEAD. Normal bearer authentication also rejects a SYSTEM database user. A partial unique index permits at most one SYSTEM-role user.
- **Authorization:** `get_current_user` validates signature and expiry, loads the user from PostgreSQL for every request, and rejects inactive users. Role claims are validated but permissions use the current database role, so role changes affect existing tokens. `require_roles(...)` provides reusable role gates for later routes. SYSTEM is never an allowed normal route role.
- **Development limitations:** Tokens are stateless and are not individually revocable; deactivation and expiry are enforced. There is no refresh-token flow, password-reset process, rate limiting, OAuth provider, production identity lifecycle, or frontend login page. Protect and rotate local secrets, and replace the demo credentials before any non-local use.

## Stage D: Core ticket APIs and business logic

- **Ticket ownership and roles:** Members list and read tickets only when `member_id` matches their authenticated database user. Support Agents and Support Heads use separate queue/detail routes. Support role dependencies are enforced by FastAPI, while services check Member ownership before returning a ticket. There is no ticket deletion API; history remains protected by the existing restrictive foreign key.
- **Ticket numbering:** Inserts use PostgreSQL `ticket_number_seq` through the existing `next_ticket_number()` column default. The function calls `nextval()` once and pads to a minimum width of four digits, so SQLAlchemy and direct SQL inserts use the same concurrency-safe sequence.
- **Ticket/SLA presence invariant:** Migration 0003 installs deferred PostgreSQL constraint triggers that require a `ticket_sla` row for every surviving ticket at transaction end and reject deleting or moving the last SLA row away from an existing ticket. A statement-level `BEFORE TRUNCATE` trigger also rejects truncating `ticket_sla`. This allows the normal service to insert the ticket and SLA in one transaction and prevents direct SQL writes from committing an orphan. Migration 0003 validates existing rows and refuses to proceed if any ticket lacks SLA state. If a legacy or manually corrupted database is found without an SLA row, stop processing the affected ticket and restore only truthful SLA values from an authoritative backup/source; do not synthesize start/deadline/pause values or silently repair it. If truthful state cannot be established, keep the record quarantined from SLA operations and resolve it as a data-integrity incident.
- **Workflow:** Support transitions are limited to `OPEN → IN_PROGRESS`, `OPEN → ESCALATED`, `IN_PROGRESS → RESOLVED/ESCALATED`, `REOPENED → IN_PROGRESS/ESCALATED`, and `ESCALATED → IN_PROGRESS/RESOLVED`. Escalation requires a reason, records history, and creates a Support Head notification. Returning from escalation restores the saved prior workflow status. Only the Member can confirm `RESOLVED → CLOSED`. Reopening is CLOSED-only, following the later explicit Stage D.2 approval; this intentionally resolves the earlier member-flow diagram that depicts reopening directly from RESOLVED. Eligibility is measured from `resolved_at` and enforces the configured window, attempt limit, and mandatory reason under a ticket row lock.
- **Priority and SLA:** Category settings supply priority at creation. A support priority override records its reason and sets the deadline to `started_at + new_priority_TAT + accumulated_pause_duration`. Active elapsed time is the time from `started_at` to `now` (or to `paused_at` while paused), less accumulated paused seconds; remaining active time is the new TAT minus that elapsed time. The original SLA start and accumulated pause seconds are preserved. An active pause is added to the deadline when the SLA resumes.
- **SLA pause/resume:** Support can mark a public reply as an information request while a ticket is in any supported non-terminal status (`OPEN`, `IN_PROGRESS`, `REOPENED`, or `ESCALATED`). Pausing preserves that status. The Member's next reply accumulates whole paused seconds, extends `due_at` by the same duration, and resumes the SLA without changing workflow status. Terminal `RESOLVED` and `CLOSED` tickets cannot be paused. Reopening starts a new SLA cycle at the current priority's TAT and records `SLA_RESTARTED`. Timestamps are aware UTC values and TAT runs 24/7.
- **History and privacy:** User-caused events store the authenticated user as the non-null history actor. Reply history stores metadata without message content. Internal replies and their history markers are omitted from Member responses. Automatic SLA escalations run every 60 seconds and record the seeded SYSTEM user as actor; escalation history and Support Head notifications are committed atomically with ticket state.
- **Notifications and dashboard:** In-app notifications are stored for ticket creation, assignment, replies, information requests, resolution, closure, reopening, and escalation. Dashboard open and category counts cover OPEN, IN_PROGRESS, and REOPENED tickets. Overdue counts include all unresolved statuses, including ESCALATED, when the SLA is unpaused and past due; escalated count is reported separately. Resolved-today counts tickets whose current `tickets.resolved_at` is within the Asia/Kolkata calendar day; reopening clears that current field, so the ticket no longer counts as currently resolved even though its completed SLA cycle remains historical. Average resolution time averages completed SLA cycles using each cycle's `started_at` to `resolved_at`, less that cycle's recorded whole-second pause duration. Unresolved and invalid cycles are excluded; the metric is `null` if no valid completed cycles exist and is rounded to two decimal hours.
- **SLA cycle history:** `ticket_sla` remains the mutable current operational state. `ticket_sla_cycles` stores cycle 1 at ticket creation and a new sequential row for each reopening. Each cycle snapshots its priority, accumulates pauses on resume (including an open pause at resolution), and finalizes resolution and optional member closure timestamps once. PostgreSQL checks require nonnegative pause duration, resolution no earlier than start, and total pauses no longer than elapsed cycle time. Historical cycle rows are not rewritten when a later cycle starts. Existing tickets are backfilled with the latest known cycle; earlier overwritten cycles cannot be reconstructed from the prior mutable SLA state. Migration 0002 refuses to run if any existing ticket lacks a `ticket_sla` row, reporting sample IDs and requiring truthful SLA state to be restored rather than inventing timestamps or durations.
- **Configuration:** Support Heads can update category priority mappings, priority TAT hours, and reopen settings. Support Agents can use support queues and dashboards but cannot modify configuration. Current settings retain the latest updater and update time; each actual setting change is also recorded in `configuration_audit` with the actor and old/new JSON values. PostgreSQL row triggers reject `UPDATE` and `DELETE`, and a statement-level trigger rejects `TRUNCATE`. The Compose `POSTGRES_USER` is the bootstrap database owner/superuser and is also used by the backend unless deployment configuration separates it; the triggers stop accidental mutation, but a privileged owner/superuser can alter or disable them. Production deployments should use a least-privilege runtime database role distinct from the migration/bootstrap owner. Configuration changes affect future tickets and explicit priority overrides, not existing ticket SLA snapshots.
- **Migration downgrade warnings:** Downgrading from revision `0002_sla_cycles_config_audit` permanently deletes all `ticket_sla_cycles` and `configuration_audit` records. Back up or export these records before downgrade if they must be preserved; the downgrade is not reversible without such a backup. Downgrading revision `0003_ticket_sla_audit_guards` deletes no application data, but removes deferred ticket/SLA presence guarantees and the audit-table TRUNCATE guard. After that downgrade, tickets can commit without SLA rows and `configuration_audit` can be truncated; do not run the older schema unless those integrity risks are acceptable. Re-upgrading 0003 restores the guards after validating current ticket/SLA consistency.
- **Automatic SLA escalation:** APScheduler runs an in-process job every 60 seconds. A ticket is eligible only when status is OPEN, IN_PROGRESS, or REOPENED, it has no `resolved_at` or `closed_at`, its SLA is unpaused, and `due_at` is earlier than the UTC execution time. Each escalation uses the seeded, active, passwordless SYSTEM user; saves `previous_status`; sets status and `ticket_sla.escalated_at`; appends escalation and status history with reason `SLA deadline exceeded (automatic timeout)`; and creates in-app notifications for active Support Heads. Manual escalation remains supported through the same shared state/history/notification helper.
- **Escalation reliability and deployment:** Candidate discovery is followed by an independent per-ticket transaction. The job locks the ticket with `FOR UPDATE SKIP LOCKED`, locks the SLA row, and rechecks eligibility before applying changes; transaction commit covers ticket, SLA, history, and notifications together. Failures roll back for that ticket, are logged, and do not prevent later candidates from processing. Repeated and overlapping invocations do not duplicate changes because a successful ticket is no longer eligible and competing invocations skip its row. A process-local lock and lifespan reference count ensure overlapping FastAPI lifespan entries share one APScheduler instance and it shuts down after the last lifespan exits. APScheduler's `max_instances=1` only coordinates executions within that scheduler process; database row locking prevents duplicate ticket effects across processes, but does not provide distributed scheduler coordination or a global lease. The current application has no setting to disable scheduling on API workers, so the supported arrangement is one API worker process. Do not run multiple API worker processes unless duplicate polling is acceptable; row locks still prevent duplicate ticket effects. A dedicated scheduler process would require adding a scheduler-role switch first. The scheduler starts and shuts down with FastAPI lifespan and is disabled under `APP_ENV=test`.
- **Deferred behavior:** Frontend workflows and notification read-state endpoints are not included.
